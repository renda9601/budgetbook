## 1. 제품 개요

### 1.1 제품 한 줄 설명

`dad`와 `mom` 두 사람이 같은 가족의 수입, 지출, 이체와 자산을 함께 기록하고 월간·연간 흐름을 이해하는 반응형 가족 가계부 웹앱이다.

### 1.2 해결하려는 문제

- 부부의 현금, 카드, 계좌, 지역화폐 사용 내역이 여러 곳에 흩어져 있다.
- 가족 전체 소비와 개인별 소비를 함께 보기 어렵다.
- 이번 달 지출이 늘거나 줄어든 이유를 실제 거래까지 따라가며 확인하기 어렵다.
- 수기 입력과 금융기관 파일을 한곳에서 관리하기 어렵다.

### 1.3 제품 목표

- 부부가 하나의 가족 거래 원장(모든 실제 거래가 모이는 기준 목록)을 함께 사용한다.
- 가족 전체와 `dad`/`mom` 각각의 수입·지출을 구분한다.
- 현금, 신용카드, 은행 계좌, 지역화폐를 같은 흐름에서 관리한다.
- 월 전체 현황에서 변화 원인, 카테고리, 실제 거래까지 자연스럽게 이동한다.
- PC, Tablet, Mobile에서 같은 데이터와 기능을 사용한다.
- 수기 입력을 먼저 안정화하고 CSV/Excel 가져오기, 자동 수집 순서로 확장한다.

### 1.4 목표가 아닌 것

- 편한가계부의 화면, 문구, 색상, 아이콘, 배치를 그대로 복제하지 않는다.
- 은행 사이트 보안 우회, 자동 로그인, 자격증명 자동 입력, 내부 API 역분석은 제품 기능이 아니다.
- MVP 단계에서 모든 자동화와 고급 분석을 한꺼번에 만들지 않는다.
- PC와 Mobile에 서로 다른 DB나 서로 다른 업무 규칙을 만들지 않는다.

## 2. 사용자와 가족 구조

### 2.1 기본 사용자

| 구분 | 의미 | 기본 요구 |
|---|---|---|
| `dad` | 가족 구성원 1 | 로그인, 공동 데이터 조회, 거래 관리 |
| `mom` | 가족 구성원 2 | 로그인, 공동 데이터 조회, 거래 관리 |
| `family/common` | 필요할 때 사용하는 공동 구분 | 실제 사용 사례를 확인한 뒤 도입. 기본값으로 성급히 추가하지 않음 |

### 2.2 사용자 관련 원칙

- `dad`와 `mom`은 같은 household(가족 묶음)에 속한다.
- “거래를 사용한 사람”과 “거래를 입력한 로그인 사용자”를 구분할 수 있어야 한다.
- 표시 이름과 인증 시스템의 실제 사용자 번호를 같은 값으로 가정하지 않는다.
- 가족 공동 거래가 필요하면 `family/common`의 의미를 먼저 정의한다.
- 두 사용자 모두 거래 등록·조회·수정·삭제가 가능하다는 기존 요구는 유지한다.
- 가족 구성원과 설정을 누가 관리할 수 있는지는 DB 변경 전에 별도로 확정한다.

## 3. 관리 대상과 핵심 용어

### 3.1 거래 유형

| 유형 | 의미 | 합계 규칙 |
|---|---|---|
| 수입 | 가족 자산으로 돈이 들어옴 | 수입 합계에 포함 |
| 지출 | 가족 자산에서 돈이 나감 | 지출 합계에 포함 |
| 이체 | 한 가족 자산에서 다른 가족 자산으로 이동 | 수입·지출 합계에 중복 포함하지 않음 |

이체는 출발 자산과 도착 자산을 모두 표현해야 한다. 카드 대금 납부를 이체로 볼지 등 세부 회계 규칙은 구현 전에 결정한다.

### 3.2 자산/결제수단

- 현금
- 신용카드
- 은행 계좌
- 지역화폐

각 항목은 이름, 종류, 사용 여부를 관리할 수 있어야 한다. 카드와 계좌를 하나의 자산 구조로 합칠지는 DB 설계 단계에서 확정한다. 카드 결제 계좌, 결제일, 계좌 잔액 같은 상세 정보는 단계별 필요성에 따라 추가한다.

### 3.3 거래 기본 정보

거래는 최소한 다음 개념을 표현해야 한다.

- 가족
- 거래를 사용한 사용자: `dad`, `mom`, 필요 시 `family/common`
- 거래를 입력한 사용자
- 수입/지출/이체
- 날짜
- 금액
- 출발 또는 도착 자산/결제수단
- 카테고리
- 내용/사용처
- 메모
- 데이터 출처: `manual`, `csv`, `excel`, 향후 `sms`, 기타
- 가져온 거래의 중복을 구분하는 값
- 생성일과 수정일

### 3.4 카테고리

- 수입 카테고리와 지출 카테고리를 구분한다.
- 대분류와 소분류를 표현할 수 있어야 한다.
- 통계의 카테고리 합계에서 실제 거래 목록으로 이동할 수 있어야 한다.
- 카테고리 추가, 수정, 정렬, 비활성화를 고려한다.
- 사용 중인 카테고리를 삭제할 때 기존 거래를 잃지 않아야 한다.

## 4. 핵심 사용자 경험

### 4.1 전체 정보 구조

- 내역
- 달력
- 자산
- 통계
- 예산
- 보고서
- 설정

이 메뉴 이름과 정보 구조는 편한가계부를 참고할 수 있지만 독자적인 디자인과 사용 흐름으로 구현한다.

### 4.2 통계 탐색 흐름

```text
전체 현황
→ 증가/감소한 원인
→ 세부 카테고리 또는 사용자/결제수단
→ 실제 거래내역
```

차트는 장식이 아니라 실제 거래를 이해하기 위한 이동 경로여야 한다.

### 4.3 내역 UX

- 선택 월의 거래 목록
- 전체/수입/지출/이체 합계
- 날짜, 사용자, 유형, 자산/결제수단, 카테고리, 내용, 금액 표시
- 최신순/오래된순 정렬
- 유형, 사용자, 자산/결제수단, 카테고리 필터
- 거래 등록, 수정, 삭제
- 삭제 전 확인 또는 되돌리기
- 데이터가 없을 때 안내

### 4.4 달력 UX

- 날짜별 수입과 지출 금액 표시
- 월 전체 수입과 지출 요약
- 날짜 선택 시 그날의 거래 목록 표시
- 달력과 내역은 같은 거래 데이터를 사용

### 4.5 거래 입력 UX

- 수입/지출/이체 선택
- 날짜, 금액, 사용자, 카테고리, 자산/결제수단, 내용/사용처, 메모 입력
- 이체는 출발 자산과 도착 자산 선택
- 필수값과 잘못된 입력을 쉬운 문장으로 안내
- 저장 실패 시 사용자가 알 수 있어야 하며 입력값을 잃지 않아야 함

### 4.6 반응형 UX

- PC: 좌측 메뉴 + 메인 콘텐츠 + 필요 시 우측 입력/상세 패널
- Tablet: 중간 폭에서도 목록과 입력을 사용할 수 있는 유연한 배치
- Mobile: 하단 메뉴 + 메인 콘텐츠 + 전체 화면 입력 또는 Bottom Sheet(아래에서 올라오는 패널)
- 모바일에서 긴 PC 표를 단순 축소하지 않고 읽기 쉬운 거래 카드/목록을 고려
- 모든 화면 크기에서 기능과 데이터 의미는 동일

## 5. 기능 요구사항

### 5.1 인증과 공동 사용

- Supabase Auth를 사용한다.
- `dad`와 `mom`이 각자 로그인한다.
- 두 계정은 같은 가족 데이터에 접근한다.
- RLS(Row Level Security, 로그인 사용자별 DB 접근 제한)로 가족 외 접근을 막는다.
- 비밀번호를 localStorage 등에 평문 저장하지 않는다.
- 운영 환경에서 Supabase 설정이 없을 때 데모 데이터가 실제 데이터처럼 조용히 표시되지 않아야 한다.

### 5.2 거래 관리

- 거래 등록, 조회, 수정, 삭제
- 월별 거래 조회
- 수입, 지출, 이체 처리
- 사용자, 자산, 카테고리 연결
- 고정비 여부와 할부 여부에 대한 기존 정보 보존
- 거래 수정일과 입력자 추적
- 수기/가져오기 출처 구분

### 5.3 합계와 통계

- 월 총수입, 총지출, 잔액
- 전체/수입/지출/이체 합계
- 전월 대비 지출 증감액과 증감률
- 사용자별 지출
- 결제수단/자산별 지출
- 카테고리별 지출과 비율
- 고정비/변동비 비교
- 기간별 수입·지출·잔액 변화
- 통계 결과에서 해당 거래로 이동

### 5.4 예산

- 월과 카테고리별 예산 설정
- 실제 사용액과 남은 금액
- 사용률 표시
- 초과 여부 표시
- 예산에서 해당 카테고리 거래로 이동

### 5.5 보고서

- 월간/연간 수입과 지출
- 합계와 평균
- 전월/전년 비교
- 사용자별, 자산별, 카테고리별 분석
- 실제 거래까지 추적

### 5.6 가져오기와 내보내기

- CSV/Excel 가져오기를 SMS 자동수집보다 먼저 구현한다.
- 가져오기 전 미리보기와 열 연결을 제공한다.
- 카드사/은행별 열 연결 규칙을 저장할 수 있도록 고려한다.
- 중복 거래를 찾아 사용자가 확인한 뒤 반영한다.
- 원본 출처와 가져온 시간을 기록한다.
- 기존 월별 Excel 내보내기 요구를 유지한다.
- Excel 내보내기는 월 요약, 거래내역, 카드/자산별, 카테고리별, 고정비/할부 정보를 포함할 수 있다.
- 금액은 숫자, 날짜는 날짜 형식으로 내보낸다.

### 5.7 고정비와 할부

- 기존 고정비/할부 조회 기능과 데이터 요구는 삭제하지 않는다.
- 고정비와 할부의 등록·수정·종료를 지원할 수 있어야 한다.
- 실제 거래와 고정비/할부 원본의 관계를 추적할 수 있어야 한다.
- 자동 반복 생성은 Future 단계에서 별도 규칙으로 확장한다.

## 6. 단계별 범위

## MVP1 — 공동 거래 원장 완성

### 목표

두 사용자가 실제 Supabase에서 안전하게 같은 가족 거래를 등록하고 월별로 관리할 수 있다.

### 포함 범위

- `dad`/`mom` 인증과 같은 household 연결
- 거래를 사용한 사람과 입력한 사람 구분
- 거래 등록·수정·삭제·목록
- 수입·지출·이체의 정확한 기본 구조
- 현금·카드·은행 계좌·지역화폐 관리
- 카테고리 대분류/소분류 기본 구조와 관리
- 월별 전체/수입/지출/이체 합계
- 월 선택과 기본 필터/정렬
- 입력 검사, 오류 안내, 빈 목록 안내, 삭제 확인/복구
- PC/Tablet/Mobile 기본 반응형 사용
- Supabase 저장과 RLS 검증
- 비밀번호 평문 저장 제거
- 거래·계산·권한의 최소 자동 테스트

### 완료 기준

- `dad`가 입력한 거래를 `mom`이 같은 가족 내에서 확인할 수 있다.
- 다른 가족 사용자는 해당 거래를 볼 수 없다.
- 수입·지출·이체가 월 합계 규칙에 맞게 계산된다.
- 이체는 출발·도착 자산을 가지며 수입·지출을 부풀리지 않는다.
- 주요 거래 기능을 PC와 Mobile에서 모두 사용할 수 있다.
- 저장 실패와 삭제 동작을 사용자가 분명히 알 수 있다.

## MVP2 — 달력과 원인 분석

### 목표

월간 소비 변화를 쉽게 발견하고 그 이유를 실제 거래까지 확인할 수 있다.

### 포함 범위

- 월 달력과 날짜별 수입/지출
- 날짜 선택 후 해당 날짜 거래
- 내용/사용처/메모 검색
- 사용자·유형·자산·카테고리 필터
- 전월 대비 지출 변화
- 사용자별 지출 통계
- 결제수단/자산별 지출 통계
- 카테고리별 지출 금액과 비율
- 기간별 수입·지출·잔액 흐름
- 고정비/변동비 통계
- 통계에서 실제 거래로 이동

### 완료 기준

- 사용자는 이번 달 지출 증감 원인을 카테고리·사용자·자산으로 확인할 수 있다.
- 통계 항목을 선택해 해당 실제 거래 목록을 볼 수 있다.
- 달력과 내역의 금액이 같은 거래 원장을 기준으로 일치한다.

## MVP3 — 예산, 보고서, 파일 연동

### 목표

소비 계획과 장기 흐름을 관리하고 외부 거래 파일을 안전하게 통합한다.

### 포함 범위

- 카테고리별 월 예산, 실제 사용액, 사용률, 초과 표시
- 월간/연간 보고서
- 합계, 평균, 전월/전년 비교
- 자산 변화 분석
- CSV/Excel 가져오기
- 가져오기 미리보기, 열 연결, 중복 검출, 출처 기록
- 카드사/은행별 가져오기 규칙 고려
- Excel 내보내기 고도화
- 고정비/할부 등록·수정·종료와 실제 거래 연결

### 완료 기준

- 예산과 실제 사용액이 거래 원장과 일치한다.
- 연간 보고서에서 합계·평균·전년 비교를 확인할 수 있다.
- 같은 파일을 다시 가져올 때 중복 후보를 식별한다.
- 사용자가 미리보기를 확인하기 전에는 가져온 거래가 확정되지 않는다.

## Future — 자동화와 고급 분석

- SMS/알림 자동수집
- 자동 카테고리 분류
- 반복 거래와 고정비 자동 생성
- 영수증/이미지 첨부 및 인식
- 이상 지출, 예측 등 고급 분석
- 더 다양한 금융기관 파일 형식 지원

Future 기능은 별도 PRD와 개인정보·권한·중복 처리 검토 후 시작한다. SMS 기능을 위해 은행 보안 우회나 자동 로그인을 사용하지 않는다.

## 7. 비기능 요구사항

### 7.1 기술

- Next.js App Router + React + JavaScript 유지
- 사용자 승인 없이 TypeScript 전환 금지
- Supabase DB/Auth/RLS 사용
- Vercel 초기 배포 고려
- 꼭 필요한 경우에만 새 라이브러리 추가

### 7.2 보안과 개인정보

- 비밀번호, 계좌번호, 인증정보, 비밀 키를 코드·문서·로그에 저장하지 않는다.
- service role key를 브라우저에 노출하지 않는다.
- 가족별 데이터 접근을 RLS로 제한한다.
- 금융 데이터가 담긴 CSV, Excel, 이미지의 저장·Git 추적 여부를 확인한다.
- 삭제와 내보내기는 실수 방지 절차를 제공한다.

### 7.3 정확성

- 같은 거래 원장을 내역, 달력, 통계, 예산, 보고서가 함께 사용한다.
- 수입·지출·이체 합계 규칙을 모든 화면에서 동일하게 적용한다.
- 금액 계산은 표시용 반올림과 저장값을 구분한다.
- mock 데이터와 실제 데이터를 명확히 구분한다.

### 7.4 사용성

- 중학생도 이해할 수 있는 쉬운 한국어 문구를 우선한다.
- 저장 성공/실패, 삭제, 빈 상태를 분명히 알린다.
- 모바일에서 가로 넘침, 하단 메뉴 가림, 작은 터치 영역을 피한다.
- 색상만으로 수입·지출·오류를 구분하지 않는다.

### 7.5 유지보수

- 한 화면 파일에 모든 기능을 계속 추가하지 않고 책임별로 나눈다.
- 기능 변경과 대규모 리팩터링을 한 작업에 섞지 않는다.
- 기존 기능·DB를 삭제하거나 이름 변경하기 전에 영향과 migration 계획을 보고한다.
- 주요 계산, CRUD(등록·조회·수정·삭제), RLS는 테스트한다.

## 8. 현재 구현에서 이어받을 내용

삭제하지 않고 유지·개선할 기존 자산:

- Next.js/React/JavaScript 기반
- household, profile, household member 방향
- 수입/지출/이체 유형
- 현금/카드/은행/지역화폐 개념
- 월별 목록·합계, 전월 비교와 차트 계산
- 거래 등록·수정·삭제 화면
- PC 좌측 메뉴와 Mobile 하단 메뉴 기본 구조
- 고정비/할부 데이터와 조회 화면
- Excel 내보내기
- Supabase Auth/DB/RLS 초안
- 데모 데이터와 계산 코드의 개발·테스트 참고 가치
- 은행 도구의 출처 표시와 중복 키 아이디어

현재 구현되어 있다는 이유만으로 완성으로 보지 않는 항목:

- Supabase 운영 연결
- 사용자 UUID 연결
- 실제 이체 구조
- 대분류/소분류
- 고정비/할부 자동 반영
- 통계에서 거래로 이동
- 반응형 실제 기기 검증

## 9. 범위 밖 또는 별도 관리

- 현재 저장소의 우리은행 사이트 수집 도구는 가족 가계부 핵심 범위가 아니다.
- 사용자 승인 없이 삭제하거나 확장하지 않는다.
- 은행 보안 우회와 자동 로그인 크롤링은 구현하지 않는다.
- 금융기관 연동은 CSV/Excel 가져오기를 우선한다.
- 송금, 실제 결제, 계좌정보 변경은 이 제품의 기능이 아니다.

## 10. 구현 전에 결정할 사항

다음 항목은 기존 코드와 문서만으로 확정되지 않았다.

1. `family/common` 거래의 정확한 의미와 합계 방식
2. 카드 사용과 카드 대금 출금을 각각 어떻게 기록할지
3. 카드 대금 납부를 이체로 처리할지
4. 카드와 계좌를 하나의 자산 표로 통합할지
5. 계좌의 시작 잔액과 현재 잔액을 앱이 계산할지
6. owner/member의 가족 설정 권한 차이
7. 거래 삭제를 완전 삭제로 할지 복구 가능한 삭제로 할지
8. 고정비·할부 자동 생성의 정확한 규칙

이 결정이 DB에 영향을 주면 `AGENTS.md`에 따라 먼저 migration 계획을 보고하고 승인받는다.

## 11. 제품 성공 기준

- 부부가 같은 가족 데이터로 일상 거래를 빠짐없이 관리할 수 있다.
- 월별 수입·지출 합계가 실제 거래 목록과 일치한다.
- 사용자는 지출 변화의 원인을 실제 거래까지 확인할 수 있다.
- 사용자별, 자산별, 카테고리별 금액을 신뢰할 수 있다.
- PC, Tablet, Mobile 중 어느 기기에서도 핵심 거래 기능을 사용할 수 있다.
- 가져오기 기능은 중복 거래를 통제하고 원본 출처를 추적한다.
- 가족 외 사용자가 데이터에 접근할 수 없다.

## 12. 개발 및 변경 원칙

- 이 PRD는 기존 유효 요구를 통합한 기준 문서다.
- 실제 구현 시 `AGENTS.md`의 범위 제한, 보안, DB migration 규칙을 함께 따른다.
- 한 번의 작업에서는 승인된 단계와 기능만 수정한다.
- 기존 기능과 UI를 명시적 요청 없이 삭제하거나 전면 재설계하지 않는다.
- 구현 완료 보고에는 변경 파일, 변경 이유, 검증 결과, 남은 위험을 한국어로 기록한다.
