# 가족 가계부 프로젝트 진단 보고서

> 진단일: 2026-08-12  
> 범위: 저장소의 소스, 설정, SQL, 기존 문서  
> 원칙: 코드·DB·패키지·환경변수는 바꾸지 않았다. 확인할 근거가 없는 내용은 **확인되지 않음**으로 적었다.

## 1. 현재 프로젝트 요약

현재 저장소에는 목적이 다른 두 프로그램이 함께 있다.

- **가족 가계부 웹앱:** `app/`, `lib/`, `supabase/` 중심이다. Next.js 한 페이지에서 로그인, 대시보드, 거래 목록과 등록·수정·삭제, 고정비/할부 조회, 설정 조회, Excel 내보내기를 제공한다.
- **우리은행 거래내역 수집 도구:** `src/`, `config/`, `tests/`, `data/`, `logs/` 중심이다. Playwright(사람 대신 브라우저 화면을 조작하는 도구)로 은행 표를 읽어 CSV와 JSON으로 저장한다.

가계부 쪽은 요청한 Next.js, React, JavaScript, Supabase, 반응형 웹 방향과 맞는다. 그러나 Supabase 환경변수가 비어 현재는 샘플 데이터와 localStorage(브라우저 내부 저장 공간)를 쓰는 데모 모드다. Vercel 실제 배포와 원격 DB 적용 여부는 **확인되지 않음**이다.

앞으로의 중심은 가족 가계부 웹앱이어야 한다. 우리은행 사이트 직접 크롤링 도구는 핵심 기능에서 제외하고, 실제 금융자료 연동은 SMS보다 먼저 CSV/Excel 가져오기를 검토하는 방향이 현재 목표에 더 잘 맞는다.

현재 주요 구조는 다음과 같다.

```text
budgetbook/
├─ app/          가계부 화면, CSS
├─ lib/          계산, 저장, Excel, Supabase 연결
├─ supabase/     DB 구조와 초기 데이터 SQL
├─ src/          우리은행 수집 도구
├─ config/       은행 도구 설정
├─ tests/        은행 도구 테스트
├─ data/, logs/  은행 도구 결과용
├─ README.md
└─ MVP_WORK_SUMMARY.md
```

루트 파일 확인:

| 항목 | 상태 |
|---|---|
| `AGENTS.md` | 없음 |
| `memory.md` | 없음 |
| `README.md` | 있음. 가계부가 아니라 우리은행 도구만 설명 |
| `docs/` | 기존에는 없음. 이번 요청으로 이 진단 문서만 추가 |
| `MVP_WORK_SUMMARY.md` | 있음. 가계부 구현 요약이지만 실제 운영 검증 전 내용 포함 |

## 2. 현재 기술 스택

| 기술 | package.json | lock 파일 실제 버전 | 사용 상태 |
|---|---:|---:|---|
| Next.js | `^14.2.5` | 14.2.35 | App Router 사용, 목표와 일치 |
| React / React DOM | `^18.3.1` | 18.3.1 | 목표와 일치 |
| JavaScript | 해당 없음 | 해당 없음 | TypeScript 아님, 목표와 일치 |
| Supabase JS | `^2.45.4` | 2.109.0 | 인증과 DB 접근에 사용 |
| Recharts | `^2.12.7` | 2.15.4 | 차트에 사용 |
| ExcelJS | `^4.4.0` | 4.4.0 | Excel 내보내기에 사용 |
| lucide-react | `^0.468.0` | 0.468.0 | 아이콘에 사용 |
| Playwright | `^1.54.2` | 1.61.1 | 가계부가 아닌 은행 도구와 테스트에 사용 |

주요 라이브러리는 모두 어딘가에서 사용된다. Playwright는 가계부에는 필요 없지만 은행 도구에는 필요하므로 저장소 전체 기준 미사용은 아니다. 다른 완전 미사용 패키지는 **확인되지 않음**이다.

`package.json`의 중요한 충돌:

- `npm run dev`와 `npm run build`는 Next.js용이다.
- `npm start`는 Next.js 운영 서버가 아니라 우리은행 도구인 `node src/index.js`를 실행한다.
- `npm test`는 은행 도구만 검사하고 가계부는 검사하지 않는다.
- Vercel 전용 설정과 배포 성공 여부는 **확인되지 않음**이다.

- 월별 Excel 내보내기
- PC 좌측 메뉴와 모바일 하단 메뉴
- localStorage 데모 저장
- Supabase SQL과 RLS(DB에서 가족 데이터 접근을 막아 주는 보안 규칙) 초안
- 별도의 우리은행 CSV/JSON 수집 도구

미완성 기능:

- 이체는 유형만 있고 보내는 자산과 받는 자산을 함께 기록하지 못한다.
- 설정, 고정비, 할부는 조회만 되고 관리 기능이 없다.
- 차트에서 원인 카테고리와 실제 거래로 내려가는 연결이 없다.
- 아빠/엄마별 합계·차트, 자산 잔액, 친절한 오류 안내, 삭제 확인이 없다.
- 실제 Supabase 저장은 환경변수가 비어 있어 **확인되지 않음**이다.

구현되지 않은 기능:

- 달력과 날짜별 거래
- 내용 검색
- 실제 대분류/소분류 UI
- 예산, 연간 보고서, 전년 비교
- 결제수단별 상세 통계
- 가계부 CSV/Excel 가져오기
- 은행 도구 결과와 가계부 DB 연결

## 4. 현재 데이터 구조

SQL에서 확인한 표:

| 표 | 역할 |
|---|---|
| `households` | 가족 묶음 |
| `profiles` | Auth 사용자 표시 정보 |
| `household_members` | 가족과 사용자의 연결, owner/member 역할 |
| `cards` | 카드 |
| `accounts` | 현금·은행·지역화폐 |
| `categories` | 수입·지출 카테고리, 상위 카테고리 연결 가능 |
| `transactions` | 거래 원본 |
| `fixed_expenses` | 고정비 원본 |
| `installments` | 할부 원본 |

현재 거래 필드:

```text
id, household_id, transaction_date, type, amount,
payment_method, account_id, card_id, category_id,
merchant, memo, owner_user_id, created_by,
is_fixed, is_installment, created_at, updated_at
```

필요 개념 평가:

| 개념 | 가능 여부 | 설명 |
|---|---|---|
| 사용자 | 일부 | Auth/profile은 있으나 거래에는 실제 사용자 번호 대신 `dad`/`mom` 글자를 저장 |
| 가족 | 가능 | `household_id` 존재 |
| 거래·금액·날짜 | 가능 | 거래 표, 0 이상 정수 금액, 날짜 존재. 거래 시간은 없음 |
| 거래유형 | 일부 | income/expense/transfer 값은 있으나 이체 정보 부족 |
| 자산·결제수단 | 일부 | 현금/은행/지역화폐와 카드가 서로 다른 표이며 이체 양쪽 자산을 못 담음 |
| 카테고리 | 일부 | SQL의 `parent_id`는 있으나 seed·화면은 한 단계만 사용 |
| 메모 | 가능 | `memo` 존재 |
| 데이터 출처 | 불가능 | manual/csv/sms 필드 없음 |

사용자 구분은 로그인 계정 `dad@family.local`, `mom@family.local`과 화면의 `dad`/`mom` 글자를 사용한다. `owner_user_id`는 실제 사용한 사람, `created_by`는 입력한 사람 의도로 보이지만 둘 다 DB 사용자와 연결되지 않은 글자다. 화면에서 로그인한 사람이 상대방 명의 거래도 만들 수 있다. 공동 가계부에는 필요할 수 있지만 입력자는 로그인 계정에서 자동 기록해야 안전하다.

카테고리는 수입/지출을 구분한다. 이체를 고르면 지출 카테고리를 보여 주며 이체 전용 구조는 없다. 자산은 `accounts`와 `cards`로 나뉘고 `payment_method`까지 중복 저장되어 서로 맞지 않는 값이 들어갈 수 있다.

수입·지출은 월 합계에 반영하고 이체는 합계에서 제외한다. 그러나 현재 이체는 출발 자산, 도착 자산, 수수료를 표현할 수 없다.

### 현재 구조 vs 권장 구조

아래는 제안일 뿐이며 DB에 적용하지 않았다.

| 현재 구조 | 권장 구조 | 이유 |
|---|---|---|
| `owner_user_id text` | 실제 가족 구성원 UUID 연결 | 존재하는 사용자만 기록 |
| `created_by text` | `auth.uid()` UUID 자동 기록 | 실제 입력자 보장 |
| `cards`와 `accounts` 분리 | 통합 `assets` + 필요 시 카드 보조 정보 | 자산 조회·통계·이체 단순화 |
| 이체 자산 한 개 | `from_asset_id`, `to_asset_id`, 선택적 수수료 | 돈의 이동을 정확히 기록 |
| `payment_method` 중복 | 자산 종류에서 계산하거나 최소화 | 서로 다른 값 방지 |
| 카테고리 한 단계 | `parent_id`를 실제 사용한 대/소분류 | 목표 구조 충족 |
| 출처 없음 | `source`: manual/csv/sms/other | 입력 경로 구분 |
| 원본 키 없음 | `source_record_id`/`import_key` | 중복 가져오기 방지 |
| 고정비/할부 연결 없음 | 원본 규칙 ID를 거래에 연결 | 자동 생성 거래 추적 |

권장 거래 핵심 모습:

```text
transactions
- household_id
- owner_member_id        실제 사용한 사람
- created_by             실제 입력한 로그인 사용자
- type, amount, transaction_date
- from_asset_id          지출·이체 출발 자산
- to_asset_id            수입·이체 도착 자산
- category_id, merchant, memo
- source, source_record_id
- created_at, updated_at
```

## 5. 현재 화면 구조

실제 Next.js 주소는 `/` 하나다. 로그인 뒤 같은 페이지의 상태만 바꿔 대시보드, 거래내역, 거래 입력, 고정비/할부, 설정을 표시한다. 각 화면의 독립 주소가 없어 새로고침, 뒤로 가기, 특정 화면 링크 공유가 어렵다.

- PC: 248px 좌측 메뉴 + 메인 콘텐츠
- 1180px 이하: 주요 그리드를 두 열로 축소
- 760px 이하: 좌측 메뉴를 숨기고 하단 5개 탭, 한 열 배치
- 표는 가로 스크롤, 차트는 부모 폭에 맞춤

기본 반응형 틀은 있다. 실제 기기에서 클릭 크기, 키보드, 표 가독성, 메뉴 겹침을 검사했는지는 **확인되지 않음**이다. `app/page.js` 한 파일이 492줄이라 메뉴를 계속 늘리면 관리가 어려워진다.

메뉴 우선순위는 MVP1의 **내역·거래 입력·자산/결제수단·카테고리·설정**, MVP2의 **달력·통계**, MVP3의 **예산·보고서** 순서를 권장한다. PC와 모바일은 같은 데이터와 계산을 쓰고 배치만 달리해야 한다.

## 6. 잘 만들어진 부분

- `household`로 부부가 한 데이터를 공유하는 방향이 좋다.
- 모든 주요 표에 RLS를 켜려는 보안 원칙이 있다.
- 수입·지출·이체와 현금·은행·카드·지역화폐를 처음부터 고려했다.
- 계산 로직을 `lib/calculations.js`로 분리했다.
- 월 합계, 전월 비교, 최근 3개월 계산이 있다.
- DB 없이 흐름을 볼 수 있는 데모 모드가 있다.
- 저장·계산·Excel·Supabase 코드가 어느 정도 파일로 분리되어 있다.
- 모바일 하단 메뉴라는 반응형 기본 틀이 있다.
- Excel의 금액과 날짜를 실제 숫자·날짜 형식으로 저장한다.
- 은행 도구는 보안 우회를 하지 않도록 설계했다.
- 은행 정규화 데이터의 `source`와 중복 키 아이디어는 미래 가져오기에 참고할 수 있다.

## 7. 문제가 있는 부분

높은 위험부터 정리하면 다음과 같다.

1. **비밀번호 평문 저장:** “비밀번호 자동저장”을 켜면 localStorage에 비밀번호를 그대로 저장한다. 운영 전에 반드시 제거해야 한다.
2. **실제 DB 미연결:** Supabase URL과 anon key가 비어 항상 데모 모드다. SQL 적용, Auth 사용자 생성 여부는 **확인되지 않음**이다.
3. **불완전한 이체:** 보내는 자산과 받는 자산을 기록할 수 없다.
4. **약한 사용자 연결:** 거래의 사용자와 입력자가 실제 Auth 사용자 번호가 아니다.
5. **넓은 구성원 권한:** 가족 구성원이면 `household_members` 전체 작업이 가능한 RLS다. 일반 member가 구성원을 바꿀 수 있는지 점검해야 한다.
6. **오류 처리 부족:** 카드·계좌·카테고리 조회 오류를 따로 검사하지 않고 저장·삭제 실패도 화면에 안내하지 않는다.

기능 정확성 문제:

- 수입으로 유형을 바꿀 때 이전 지출 카테고리가 남을 수 있다.
- 이체가 지출 카테고리를 사용한다.
- 비카드 자산 선택 목록이 현재 결제 종류와 맞지 않을 수 있다.
- 기본 거래일이 오늘이 아니라 선택 월 1일이다.
- 0원 거래를 허용한다. 필요한지는 **확인되지 않음**이다.
- 삭제 확인과 빈 목록 안내가 없다.
- 모바일 “통계” 버튼이 고정비/할부 화면을 연다.
- PC “지출 등록” 메뉴에서 수입과 이체도 등록한다.
- “전체 입력자” 필터가 실제로는 거래 소유자를 거른다.

구조·중복·오류 가능성:

- 로그인, 메뉴, 차트, 표, 폼, 설정이 `app/page.js` 한 파일에 몰려 있다.
- 사람 이름과 카드·계좌·카테고리가 화면, 데모 데이터, seed SQL에 반복된다.
- Supabase 목록이 비면 문자열 데모 ID를 대신 쓰는데 DB 열은 UUID(긴 고유 번호)라 저장 실패 가능성이 있다.
- 여러 가족에 속하면 첫 번째 가족만 `.limit(1)`로 고르고 선택 기준이 없다.
- 고정비·할부 원본과 실제 거래가 연결되지 않아 합계가 달라질 수 있다.
- 수정·삭제가 코드에서는 가족 ID를 함께 확인하지 않고 RLS에만 의존한다.
- 실제 모바일 차트 라벨 겹침 여부는 **확인되지 않음**이다.

사용되지 않는 것으로 보이는 항목:

- `.agents/`, `logs/`는 비어 있고 `data/`에는 자리 유지 파일만 있다.
- `accountSummary()`는 현재 호출되지 않는다.
- `formatMonth()`를 `app/page.js`에서 import하지만 그 import 값은 쓰지 않는다.
- 은행 도구 파일은 웹앱에서는 사용되지 않지만 별도 도구로는 사용되므로 바로 삭제하면 안 된다.

## 13. DB 구조 개선 제안

먼저 다음 세 가지를 확정한다.

1. 사용한 사람과 입력한 사람을 분리하고 둘 다 실제 사용자 번호로 연결한다.
2. 수입은 도착 자산, 지출은 출발 자산, 이체는 출발+도착 자산으로 기록한다.
3. 처음부터 `source`와 중복 방지 키를 둔다. 수기 입력 기본값은 `manual`이다.

```text
가족
├─ 가족 구성원 ─ Auth 사용자/profile
├─ 자산
├─ 카테고리(대분류/소분류)
└─ 거래
   ├─ 사용한 구성원 / 입력 사용자
   ├─ 출발 자산 / 도착 자산
   └─ 카테고리 / 출처
```

DB 변경 전에 사용자 결정이 필요한 질문:

- 두 사람 모두 가족 설정과 구성원을 바꿀 수 있는가?
- 공동 사용 거래가 필요한가?
- 카드 사용 시점과 카드 대금 출금 시점 중 언제 지출로 보는가?
- 카드 대금 납부는 이체인가?
- 앱이 계좌 잔액을 계산하는가, 은행 잔액을 입력하는가?
- 삭제한 거래를 복구할 수 있어야 하는가?

이 답들은 코드에서 **확인되지 않음**이다.

## 14. PC/Mobile UI 구조 제안

공통 흐름은 **전체 현황 → 증가/감소 원인 → 세부 카테고리 → 실제 거래**로 한다. PC와 모바일은 같은 Supabase 데이터와 계산을 사용한다.

PC:

```text
좌측 메뉴 | 메인 콘텐츠(목록·요약·차트) | 필요할 때 오른쪽 입력/상세 패널
```

모바일:

```text
상단 월·핵심 합계
중앙 메뉴 내용
하단 내역 / 달력 / +등록 / 통계 / 더보기
+등록은 전체 화면 또는 Bottom Sheet(아래에서 올라오는 입력 상자)
```

긴 표는 모바일에서 날짜별 카드 목록으로 보여주는 편이 좋다. MVP1 메뉴는 내역·등록·자산·설정 위주로 작게 시작한다.

## 15. 보안 및 환경변수 확인사항

| 변수 | 상태 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | example/local 모두 비어 있음 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | example/local 모두 비어 있음 |
| `OPENAI_API_KEY` | local에 값 있음. 현재 코드 사용 흔적 없음, 필요 이유 **확인되지 않음** |
| `OPENAI_MODEL` | local에 값 있음. 현재 코드 사용 흔적 없음 |

`.env.local`은 `.gitignore`에 포함되어 있고 값은 이 문서에 노출하지 않았다. `NEXT_PUBLIC_` 값은 브라우저에서 볼 수 있으므로 Supabase anon key 자체보다 정확한 RLS가 중요하다. 관리자 비밀 키인 service role key는 코드와 변수 목록에서 확인되지 않았다.

필수 보안 점검:

1. localStorage 비밀번호 저장 제거
2. Auth 비밀번호·세션 정책 확인
3. owner만 구성원 관리가 가능한지 결정
4. `created_by`를 `auth.uid()`로 기록
5. 실제 Supabase RLS 테스트
6. 운영에서 데모 모드가 조용히 켜지지 않게 경고 또는 차단
7. CSV 입력 검증과 중복 방지
8. 은행 원본 파일의 개인정보 보관 기준 결정

실제 Supabase 설정, Vercel 환경변수, 배포 주소와 운영 로그는 **확인되지 않음**이다.
